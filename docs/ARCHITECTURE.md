# 設計メモ

改修する前にここを読むと事故りにくい。

## ファイル構成

```
src/
├── index.js            公開 API（ここに出したものだけが外から見える）
├── aggregate.js        集計 + 配置。React 非依存の純粋関数
└── NineGridChart.jsx   描画。集計結果を受け取って DOM にする
demo/
├── App.jsx             デモ UI（スライダー等）
├── demoData.js         ダミーデータ生成
└── main.jsx            エントリ
```

## データの流れ

```
行データ (flat rows)
    │
    │  aggregate()          ... group → item の2段で積む
    ▼                           数値は加算、数値配列は要素ごとに加算
2階層ツリー { groups, total, totalMetrics }
    │
    │  layout()             ... 中心を避けて RING 順に配置
    ▼
9ブロック × 9セル { cells, levels }
    │
    │  <NineGridChart>      ... CSS Grid でネストして描画
    ▼
DOM
```

**この3段を分けているのが設計上の要点。**

`aggregate()` と `layout()` は React に依存していないので、単体でテストできるし、
Python 版や Vue 版を作るときの移植単位もここになる。

そして将来 `mode="edit"`（手入力）を足すときは、
**`layout()` の出力形式に合わせたモデルを別ルートで作るだけ**でよく、
描画部分はそのまま再利用できる。集計と描画が癒着していると、これができない。

## RING — なぜ中心を飛ばすのか

```js
export const RING = [0, 1, 2, 3, 5, 6, 7, 8];
```

3×3 グリッドの index 4 は中心。ここは常に「そのブロックが何なのか」を示すラベルで
埋まるので、データは入らない。

順位 1 位 → index 0（左上）、2 位 → 1、… 4 位 → 3、5 位 → **5**（中心を飛ばす）、
… 8 位 → 8（右下）。結果として左上から右下へ読み順に強度が下がる。

これは中心ブロック（グループのサマリ）でも外周ブロック（アイテムの内訳）でも
同じ配列を使い回している。同じ規則で並ぶので、目が迷わない。

## 強度スケールを2つ持つ理由

`maxItemValue` と `maxGroupValue` を別々に持っている。

グループの値はアイテムの合計なので、常にアイテムより大きい。
1つのスケールで正規化すると、**外周のセルが全部ほぼ真っ白になって読めなくなる**。

そのため item は item の最大値で、group は group の最大値で正規化している。
色の濃さはブロック内での相対比較として読むのが正しい。

## 「その他」の畳み込み

`applyLimit()` が担当。3つの戦略がある。

`merge` の場合、**畳んだあとに再ソートしている**。丸めた結果の合計が
3位相当になったら3位の位置に置かれる。順位を保ったまま末尾に固定するより、
「値の降順で並ぶ」という規則が一貫して素直だと判断した。

### 「その他」ブロックの中身は二重に畳む

グループを畳むと、複数グループのアイテムが1ブロックに混ざる。
たとえば「キウイ」と「プルーン」が「その他」になると、
ヘイワード・ゴールド・サンプルーンが同じブロックに来る。

このとき同名アイテムが別グループに存在すると重複するので、
`rollup()` で名前ごとに集約し直してから、もう一度 `applyLimit()` にかけている。

## メトリクスの自動集計

`mergeMetrics()` が `valueKey` 以外の数値をすべて拾う。

- `number` → 加算
- `number[]` → 要素ごとに加算
- それ以外 → 無視

配列を要素ごとに加算する挙動が、月別売上のような系列データを
「アイテム → グループ → 総計」の各階層で自動的に積み上げてくれる。
利用側は各行に12要素の配列を1つ持たせるだけでよく、
階層ごとの前処理が一切いらない。

`skip` セットで `groupKey` / `itemKey` / `valueKey` を除外しているので、
たとえば商品コードが数値でも `itemKey` に指定されていれば足し算されない。
ただし **`itemKey` に指定していない数値 ID 列があると意図せず合算される**ので注意。
不要な列は事前に落としておくこと。

## 色

`shade(t, hue)` が HSL で明度と彩度を同時に振る。
パレット配列をハードコードすると利用側が必ず不満を持つので、
外から変えられる軸を `hue` 1つに絞ってある。

文字色は `t > 0.52` で反転する。この閾値は目視で決めた値で、
極端な hue（黄緑あたり）では最適でない可能性がある。

## スタイリングの方針

**インラインスタイルのみ。CSS ファイルも Tailwind も使っていない。**

ライブラリとして配布する以上、利用側に「CSS を import してください」を
要求しないほうが摩擦が少ない。ビルド設定もクラス名衝突も考えなくていい。

代償として利用側からのスタイル上書きがしにくい。
需要が出たら `className` / `style` の受け口と、CSS 変数によるテーマ機構を
足すことになる（現状は未対応）。

## 既知の制約

- **レスポンシブが弱い。** `minWidth` を下回ると横スクロールになる。81マスに日本語を
  入れる以上、狭い画面での根本解決は難しい。モバイルではブロック単位でページングする
  別レイアウトが要る
- **セルのラベルは2行で打ち切り**（`-webkit-line-clamp`）。長い名前は省略される。
  全文はツールチップで確認する前提
- **TypeScript 型定義がない。** `.d.ts` を手書きするか、`.tsx` へ移行するかは未決
- **ツールチップは親要素基準の絶対配置。** 親が `overflow: hidden` だと見切れる
